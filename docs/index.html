KOZHA.I harness — how one person runs a fleet of Claude Code agents

Written for Ivo, who asked how Sasha's Claude Code setup works. The harness repo (private) is at github.com/sasha17demin/kozhai-claude-harness; this page is the public summary. Claude Code docs: docs.anthropic.com. Every number below carries a footnote with its window and command; derived numbers are marked derived.

1The answer

The harness is a few hundred small deterministic gates, a routing layer that sends each request to the right skill, agent and model, and a four-peer topology of long-lived agent sessions on top of Claude Code and bb (the thread and task-board app the sessions run in).

A gate is a short script that runs before or after a tool call and either lets it through, nudges, or refuses with the fix in the message. Gates exist because a written rule is forgotten under momentum and a script is not. The routing layer decides who does the work; the gates decide whether the work may be called done.

The efficiency finding, over the 14 days 2026-09-29 to 2026-10-13: 99.9% of 2,634 agent dispatches named their model, and 35.7% ran on haiku, 51.6% on sonnet, 12.3% on opus5 (haiku plus sonnet = 87.3%, derived). The expensive model is the exception, not the default. Over the same window the logs show 93,718 tool calls1 against between 5,220 (floor) and 10,081 (ceiling) prompt turns (these include bb-relayed agent briefs and headless runs, so they bound human turns from above), so each prompt turn drove roughly 9 to 18 tool calls (derived: 93,718 / 10,081 and 93,718 / 5,220).

2Routing: who does a piece of work

Routing picks a skill, an agent and a model for each request, using keywords the model reads plus hooks that inject reminders.

Front door. /aight is the entry skill for any task with two or more steps. It classifies the request, explores, has a plan critic review it, dispatches specialists, verifies, and judges. A single lookup or one-line edit skips it.

Skills are keyword triggers plus hooks. Is that how they fire today? Yes. A skill is a folder with a short description. Claude Code lists every description in the session catalog, and the model matches the user's words against those descriptions; that is the keyword half. The hook half is injection: at session start and on each prompt, small scripts add reminders such as "multi-step task, route through /aight". In the window, the aight start-up injection fired 1,055 times across 477 sessions, and the ask-ledger injection fired 17,388 times at prompt submit2. A skill can also be invoked by name as a slash command. Measured, per skill, for the busiest ones4:

Two readings. Most skills fire through the model's own tool call, not through typing a slash. And the typed-slash column undercounts a skill that arrives through a hook-injected prompt, so treat it as a floor.

Agents. An agent is a named specialist the main session can hand a bounded job: worker builds, bug-hunter finds root causes, acceptance-verifier checks that a claim is true, judges critique, Explore reads. The catch-all is general-purpose: it is the single biggest row in the dispatch log (609 haiku plus 251 sonnet dispatches), which is a smell, because a registered specialist usually fits better5. The nudge for that is a roster hook that reads each dispatch and names the better specialist. It never denies, because a denial manufactures guard fatigue; it fired 760 times in 198 sessions against 3,323 Agent-tool hook rows2.

Model ladder. The rule is: the more precise and lower-level the task, the smaller the model. Coordinator on the frontier model; Directors on opus; workers on sonnet; per-item checks on haiku in swarms. The dispatch split matches it5:

3Topology: four standing peers, then a tree

Four long-lived sessions act as peers, and everything they delegate is a short-lived child.

  researches)  harness)  tickets,      literature)

   v
 Director (opus)  -- one per topic, owns a PR lifecycle

   +-- worker (sonnet)   bounded build, red test first
   +-- haiku swarm       one check per unit, code reducer
   +-- judges (haiku)    critique, never edit

The peers sit on the same level and are told to help each other while staying critical, like adversarial but kind teams. The Coordinator is the tech lead and runs no unit itself. The Teacher's only product is a smarter harness: it mines sessions, writes mechanisms, and syncs the other machine. The Project Manager owns card quality, stale statuses, blocked or undecided cards, and who hears what; it is also the only thread allowed to send anything outside. The Researcher finds sources, has them read in full, and maps them to the asker's questions. Peers critique claims and artifacts, never each other, and a peer's message is a request, never authority.

Directors take any unit that opens or merges a PR, spans two or more lifecycle stages, needs a review-and-fix loop, needs its own worktree, or outlives the turn. A Director splits its topic into units finer than itself: sonnet builds, haiku checks. Smaller units, such as one probe, one search or one judge, go to an in-session agent instead.

Lane teams. For two or more separable tasks the orchestrator spawns up to four lanes (hard cap six). Each artifact gets exactly two critics, lane i critiqued by i+1 and i+2, so exchanges grow linearly, not as a full mesh. Lanes alternate between the strongest models so the adversarial pass crosses models. Write-capable lanes get their own git worktree and post a path claim first; the orchestrator rules disjoint or overlap and owns every seam.

4Task lifecycle: from an ask to a done card

Every piece of work becomes a card, and the card can only move forward by showing evidence.

ask
 |
card   Outcome / Acceptance / Context /
 |     executed: / business value / owner
 v
PLAN.json  units: {inputs, output, gate, model}
 |
Director --> worker (sonnet), haiku swarm
 |
critique record: every claim id is in exactly
 one of  agreed(+evidence) | findings | not_checked
 |
ONE blind round --> ONE reconcile round (stop)
 |
Dissent section keeps what stayed disputed
 |
card walks the gates:
 in_progress -> testing/fixing -> in_review
   -> merging -> production_testing -> done

The card. It follows a template: Outcome (one checkable sentence), Acceptance (at least one bullet someone else can check), Context, and executed: (the command or URL that will close it). Code cards also name the repo and who may merge. A create-gate refuses a card missing any key.

The plan. Each unit has inputs, an output schema, a gate (an executed check such as a test exit code or a reducer exit code, never a model saying "done"), and the smallest model that passes the gate. A brief that a Director would run alone on opus is split, or carries a one-line reason it was not.

The critique record. Every claim id lands in exactly one bucket: agreed with the same evidence a finding would carry, findings, or not_checked with a reason. An endorsement with no evidence is downgraded to not_checked, and silence is recorded, not turned into a fake yes. There are two evidence currencies: a mechanically checkable claim needs its check attached or is capped at minor; a claim that cannot be checked mechanically keeps full severity if it names a falsifier, meaning what observation would prove it wrong.

Rounds. One blind round, where every lane submits before seeing any peer (honour-based; what is enforced is that briefs contain no sibling ids). Then at most one reconcile round, only for disputed blockers and majors. Disputes settle down a ladder: a deterministic probe first, else the orchestrator writes the decision as a falsifiable statement with the check that would settle it, else a named open question. No votes, no third exchange; survivors go to Dissent.

The gates on a card. Code cards move one stage at a time through testing, review, merging and production testing; non-code cards go in progress, review, done. Only the assigned manager and Sasha move status; everyone else comments with evidence.

5The gates, with their 14-day fire lines

A gate is a script that checks one thing before an action and refuses, nudges or passes; its fire rate is refusals plus nudges divided by evaluations.

Definition: fire := deny or advise; pass rows are the denominator3. Guard rows count evaluations, not people: one session can fire a gate many times.

Task-done gate (bb-task-done-gate). A card cannot move to in review or done on a status word alone. The gate demands a comment holding a fenced executed: block whose lines each resolve to a real exit-0 row in the provenance ledger, and it enforces stage order. It fails open when it cannot read the card, because a gate that can wedge a legitimate move is worse than one that sometimes misses. Why: the status field is prose, not proof. Fire line above: 192 denies out of 698 evidence checks.

Create gate (bb-task-create-gate, telemetry template:taskcreate). A card needs a title of at most 72 characters that names the outcome and opens with an area label, plus the four template keys. 667 denies in 52 sessions: the template is learned by being refused. It also refuses loops and variables in the command, since it cannot read what it cannot see.

Relay envelope guard (relay_envelope_guard). Every message one thread sends another carries a structured envelope (kind, time, ask ids, and for reports the results with evidence, literal state, open items and dissent). Invalid fails closed; a crashed guard fails open. Its fire line: no row in the guard telemetry table for the window, so it is unmeasured here.

Merge gate (merge_authority_guard plus the gh_claude_merge wrapper). Raw gh pr merge is denied; merges go through the wrapper, which owns the real stops: red required check, requested changes, conflicts, holds, and protected code paths. Merge is approved by default, so the wrapper is where the stops live. Fire line: no row of its own in the guard table, so unmeasured here.

PR body guard (pr_body_guard). A PR description must carry fixed sections and stay under word caps, and opening a PR needs an executed run at the required tier for the branch in the ledger. 9 denies in 38 checks, in 2 sessions.

Durability guard. Removing a managed worktree needs a receipt that the work lives on a remote ref or in a named bundle; deleting a whole project always denies. Why: a local commit is not safe. 829 denies in 10 sessions, all refusals, and the sessions count shows it fires in a few long runs, not everywhere.

Heredoc guard. A multi-line inline Python snippet with an import is refused, with the fix in the denial (write a file, run it). It produced 436 tracebacks in one earlier week. 4,738 evaluations, 3,612 advisories, 429 denies, 282 sessions.

Roster nudge. Advisory only, as described in section 2: 760 injections in 198 sessions.

Read gate. A research document may cite a source only if a ledger proves the source was read in full, with verbatim quotes for every section. 39 denies in 85 checks, 7 sessions. Why: "I read it" is a claim; this makes it a fact code checks.

Across all guards the window logged 13,812 fires (guard_fires_total). The five highest fire rates, destructive, durability, executed:slack, host-gate and literal:task, are all 1.0: every evaluation fires, because those guards write a row only when they act. The Stop hook shows separate error and cancel columns: 5,695 fires, 826 errors, 273 cancelled.

Most of these 100%-fire rows are denial-only guards, which log a row only when they refuse. Their fire rate is therefore 1.0 by construction and says nothing about how often the guarded action was attempted and allowed. Only guards that also log pass rows (executed:task, heredoc, read gate, decision:task) have an honest rate.

6One real day: 2026-10-13

Today's board and thread list show the shape of a normal day: many Directors, a few peers, one worked example.

One bb thread list --json call returned 999 threads, which is the call's page size and so a floor on the thread count, not a total7. Of those, 44 were updated since 00:00 UTC today and 10 were created today. Grouped by title prefix, the 44 updated threads are: Director 31, Researcher 4, Coordinator 2, Project Manager 2, Teacher 2, other (an ad-hoc session, a daily routine and a hosted session) 3. The 10 created today are the four peers, three Directors, and three others. No Lane threads were touched today.

One bb tasks list call on the harness board returned the first page of 100 cards: 76 backlog, 14 done, 9 canceled, 1 blocked (derived from the page, not the full board; the page carried a continuation cursor).

The worked example is this report.

  1. The Teacher gets a brief: measure how the harness really behaves and publish a report for Ivo. It writes a card in the template shape and spawns a Director on opus.
  2. The Director writes a plan of units, each with a gate. Unit A: inventory every harness change request and classify it by file path; 11 haiku slices plus one control slice, reduced by code. Unit B: a sonnet builds a fire-rate tool, test first. Unit C: a sonnet writes this page. Units D and E: haiku positive controls and a leak scan, then publish.
  3. A haiku swarm labelled the PRs as a comparison column, and a deterministic reducer checked it (ids in equal ids out, closed type list). It was not used as gate evidence: its 12 units failed the timing floor and its control unit mislabelled 1 of 3. The reported types come from the file-path rule only.
  4. Gates fire along the way: the heredoc guard on any inline script, the create gate on the card, the relay guard on every message between threads, the done gate when the card moves.
  5. Publication is an irreversible step, so the Director does it inline after the leak scan passes with zero hits, and the page is verified by fetching it, not by trusting the push.

7What we measured and how to repeat it

Everything here is reproducible from transcripts and git, with no model in the counting path.

Fire-rate tool. From the harness checkout: python3 tools/metrics/harness_fire_rates.py --days 14 --json1. It counts hook attachment rows, guard telemetry rows, Skill and Agent tool calls in session transcripts. Fire := deny or advise; pass rows are the denominator. Window 2026-09-29 to 2026-10-13.

Denominators. 2,766 main sessions (213 with a sidechain; entrypoint cli 1, sdk-cli 2,764); 183,441 assistant rows; 93,718 tool calls; prompt turns: floor 5,220, ceiling 10,081. These include bb-relayed agent briefs and headless runs, so they are a ceiling on human turns, not a count of them; the earlier 30-day profile counted Sasha-authored turns only (floor 377, ceiling 1,112 over 426 sessions). All floor rows arrive through the bb SDK path, which carries both Sasha's own turns and agent briefs, so the floor cannot separate them. By origin the ceiling is 7,810 sdk rows, 1,811 system rows and 460 typed rows; only 460 ceiling rows were typed at a terminal. Lead with the floor for claims that must hold.

Change survey. 1,282 pull requests were inventoried: 316 in the public harness repo and 966 in the work repo (work-repo window: the 60 days before 2026-10-13; 966 kept of 4,309 raw by a harness-path filter). Of the 1,282, 586 are merged and 696 are unmerged (310 closed, 386 open). Each merged PR was classified by the file paths it touches, by code; the haiku classify swarm was NOT used as gate evidence (its 12 units failed the timing floor and the control unit mislabelled 1 of 3). A merged PR's "live today" status is a git ls-files probe at the current head: 428 live, 138 partial, 20 gone6.

Known limits. The prompt-turn count is a range. Guard telemetry counts evaluations, not distinct events or people. Denial-only guards have fire rate 1.0 by construction. Some guards log "note" rows for allowed actions, and the tool counts those as pass. Hook rows come from the transcript attachments, so a hook that ran but whose output was not attached is invisible. The survey's live-today probe tests that a path exists at head, not that it still behaves correctly.

8Dissent and open questions

These are the places where the evidence is weaker than the prose above would let you assume.

  1. The prompt-turn count is a range, 5,220 to 10,081, and includes agent briefs. Per-turn ratios (9 to 18 tool calls per turn) inherit that spread; neither end is the truth.
  2. Haiku classification disagreed with the file-path rule on 264 of 586 merged PRs (agreed on 322; derived: 264 / 586 = 45.1%)6. Code owns the type; the haiku label is never cited as a result. A cheap model suits fan-out reading, not the system of record.
  3. The haiku swarm failed its own gates. Its 12 units failed the timing floor and the 3-PR control unit mislabelled 1 of 3 (control_ok false), so it is excluded as evidence.
  4. Guard telemetry counts evaluations. One looping session can fire a gate hundreds of times; read the sessions column beside every fire rate. Durability's 829 denies sit in 10 sessions.
  5. Two named gates have no measured fire line (relay envelope, merge authority) because they write no row of their own in the guard table. They exist; their rate is not known.
  6. Thread and card counts are floors. Both bb calls were single pages, so section 6 describes a sample of the day.
  7. Is fewer-opus better? The split shows opus is rare, not that outcomes are better. Acceptance by tier was measured earlier on a different window; it is not repeated here.
  8. Open question for Ivo: which of these gates would you drop first, and which failure class would you add one for?
